GitHub 주간 AI·개발 이슈 자동화 마스터 사양서
Version 1.0
기준 시간대: KST (UTC+9)

======================================================================
0. 문서 목적과 적용 우선순위
======================================================================

이 문서는 매주 GitHub에서 화제가 된 AI 및 소프트웨어 개발 관련 이슈를 수집·평가·선정·분석하고,
최종적으로 Telegram을 통해 TOP 5 주간 리포트를 발송하기 위한 자동화의 최종 기준 문서이다.

이 문서는 다음 12개 세부 규칙을 하나의 실행 사양으로 통합한다.

1. 데이터 보고 기준
2. GitHub 데이터 수집 기준
3. 화제성 점수 계산 기준
4. Telegram 메시지 내용 기준
5. Telegram 메시지 형태
6. 서술형 콘텐츠 생성 규칙
7. 보고 실행 스케줄 규칙
8. 이전 주 데이터 보관 규칙
9. TOP 5 최종 예외 처리 규칙
10. 데이터 부족 및 실패 처리 규칙
11. Telegram 전송 운영 규칙
12. 검증 및 테스트 규칙

규칙 간 충돌이 있을 경우 다음 우선순위를 따른다.

1순위: 이 마스터 사양서의 명시적 규칙
2순위: 후반에 확정된 세부 규칙
3순위: 초기 데이터 보고 기준

즉, 초기 문서에 존재하는 초안 수치보다 이후 확정한 세부 규칙을 우선한다.

최종 목적은 단순한 "인기 Repository 목록"이 아니라,
"이번 주 개발자가 실제로 알아둘 가치가 있는 GitHub의 중요한 변화"를 안정적으로 전달하는 것이다.

1. 전체 자동화 목표
======================================================================

매주 최근 7일 동안 GitHub에서 다음을 탐지한다.

- 새롭게 급성장한 AI·개발 관련 Repository
- GitHub Trending에서 주목받은 프로젝트
- Issue / Pull Request / Discussions 활동이 급증한 프로젝트
- 중요한 Release
- Critical / High Security 사건
- 라이선스 변경
- API 폐기 또는 Breaking Change
- 프로젝트 유지보수 중단 또는 종료
- 개발 생태계에 영향을 주는 기술적·정책적 변화

수집한 후보를 화제성 점수와 뉴스 가치로 평가해
최종 TOP 5를 선정한다.

선정된 TOP 5는 단순 지표 요약이 아니라 다음까지 설명한다.

- 왜 이번 주에 화제가 되었는가
- 프로젝트는 무엇을 하는가
- 개발자에게 왜 중요한가
- 개발자들은 무엇을 긍정적으로 평가하는가
- 어떤 우려와 비판이 존재하는가
- 어떤 부분에서 의견이 갈리는가
- 실제 적용 시 주의할 점은 무엇인가

최종 결과는 Telegram으로 전송한다.

2. 실행 스케줄
======================================================================

2.1 실행 주기

- 실행 요일: 매주 일요일
- 실행 시간: 19:00
- 기준 시간대: 대한민국 표준시 KST (UTC+9)
- 실행 빈도: 주 1회

2.2 조사 기간

각 주간 리포트의 조사 범위는 정확히 7일(168시간)이다.

- 시작: 이전 일요일 19:00 KST 이상
- 종료: 이번 일요일 19:00 KST 미만

수식:

previous_sunday_19:00 <= event_time < current_sunday_19:00

이번 일요일 정확히 19:00에 발생한 이벤트는 다음 주 조사 기간에 포함한다.

2.3 전주 비교 기간

현재 조사 기간:
- 이번 주 실행 시점 - 7일 ~ 이번 주 실행 시점

비교 기간:
- 이번 주 실행 시점 - 14일 ~ 이번 주 실행 시점 - 7일

전주 대비 비교 대상:

- Star
- Issue
- Pull Request
- Fork
- Discussions
- 화제성 점수

최근 30일 데이터는 장기 흐름을 확인하기 위한 보조 자료로만 사용한다.

4. GitHub 데이터 수집 전략
======================================================================

수집은 혼합형으로 수행한다.

초기 운영 비중:

- GitHub Trending 기반 후보: 40%
- GitHub 전체 조건 검색 후보: 40%

이 비중은 절대적인 할당량이 아니라 후보 발굴 전략의 가이드이다.
실제 결과 품질에 따라 추후 조정할 수 있다.


======================================================================
5. GitHub Trending 기반 수집
======================================================================

목적:
이미 GitHub 커뮤니티에서 큰 관심을 받고 있는 프로젝트를 빠르게 발견한다.

후보 조건:

- 최근 조사 기간 동안 GitHub Trending에 등장
- AI 또는 소프트웨어 개발 관련
- 단순 밈성 프로젝트가 아님

Trending 평가는 가능하면 다음처럼 처리한다.

- Top 1~5: 매우 강한 신호
- Top 6~15: 강한 신호
- Top 16~30: 보통 신호
- 30위 이하: 보조 신호

수집 정보:

- Repository 이름
- Owner
- Repository URL
- 설명
- 주요 언어
- 현재 Star
- Fork
- 최근 업데이트 날짜
- 최근 Release 여부
- Trending 여부
- 가능한 경우 Trending 순위

Trending 여부만으로 최종 선정하지 않는다.


======================================================================
6. GitHub 전체 조건 검색
======================================================================

목적:
Trending에 아직 등장하지 않았지만 빠르게 성장하고 있는 프로젝트를 발견한다.

6.1 기본 후보 조건

기본적으로:

- 현재 Star 100 이상
- 최근 14일 이내 업데이트를 우선
- AI / 개발 관련성이 명확할 것

그리고 아래 중 하나 이상의 강한 신호가 존재하면 후보로 등록할 수 있다.

- 최근 7일 Star 증가량 기준 충족
- 최근 7일 Star 증가율 기준 충족
- Trending 진입
- Issue / PR 활동 급증
- Major Release
- 중요 Security 사건
- License / API / Policy 변화
- 프로젝트 종료 / 유지보수 중단
- 개발 생태계에 영향을 주는 중요한 기술 사건

모든 조건을 AND로 묶지 않는다.
"기본 관련성 + 하나 이상의 강한 신호"를 원칙으로 한다.

6.2 저장소 규모별 Star 증가 임계값

현재 Star 100~499:
- 최근 7일 +50 이상
또는
- +25% 이상

현재 Star 500~1,999:
- +100 이상
또는
- +20% 이상

현재 Star 2,000~9,999:
- +300 이상
또는
- +10% 이상

현재 Star 10,000~49,999:
- +700 이상
또는
- +5% 이상

현재 Star 50,000 이상:
- +1,500 이상
또는
- +2% 이상

절대 증가량과 증가율을 함께 고려한다.

6.3 신규 저장소 기준

생성 30일 이내:
- Star 300 이상이면 후보

생성 14일 이내:
- Star 500 이상이면 강한 신흥 후보

생성 7일 이내:
- Star 1,000 이상이면 우선 검토

신규 저장소는 증가율이 과도하게 높아질 수 있으므로
절대 Star 수와 성장 속도를 함께 본다.


======================================================================
7. Issue / PR / Discussions 활동 기준
======================================================================

7.1 Issue

최근 7일 신규 Issue:
- 10개 이상이면 활동 증가 후보

특정 Issue 댓글:
- 20개 이상: 관심 증가
- 50개 이상: 높은 관심
- 100개 이상: 강한 화제성

Security, Breaking Change, License, Deprecation, Major Bug, Performance 관련 Issue는
일반 수치 기준보다 낮더라도 중요 후보로 검토할 수 있다.

7.2 Pull Request

최근 7일 PR:
- 10개 이상: 활발
- 30개 이상: 매우 활발

대형 Repository는 평소 활동량이 높을 수 있으므로
절대 수치보다 이전 주 대비 증가율을 더 중요하게 본다.

7.3 활동 급증률

Star / Issue / PR / Discussion 등에 공통 적용 가능한 신호:

- +25%: 관심 증가
- +50%: 뚜렷한 증가
- +100%: 강한 상승
- +200% 이상: 급격한 화제성

8. Release / Security / Policy 이벤트
======================================================================

8.1 주요 Release

다음은 우선 후보로 본다.

- v1.0 또는 정식 출시
- Major Version Release
- Breaking Change
- 신규 AI 모델 지원
- 신규 API
- 아키텍처 변경
- 대규모 성능 개선
- 주요 기능 추가
- Migration 필요 변경
- Deprecation / 기능 제거

단순 Patch나 경미한 버그 수정은 기본적으로 중요 Release로 보지 않는다.

8.2 Security

다음은 Star 증가와 무관하게 반드시 검토한다.

- Critical Severity
- Remote Code Execution
- Authentication Bypass
- Privilege Escalation
- Supply-chain Attack
- Credential Exposure
- 광범위한 High Severity 취약점
- Widely-used Dependency Vulnerability

8.3 License / API / Policy

다음도 일반 인기 기준과 별개로 중요 이벤트로 본다.

- 라이선스 변경
- 상업적 사용 제한 추가
- API 폐기
- 주요 기능 제거
- 유지보수 중단
- 프로젝트 종료
- 소유권 변경
- Governance 변경
- 대규모 커뮤니티 논란
- 프로젝트 방향성 변경

10. 이전 주 데이터 보관
======================================================================

매주 일요일 19:00 KST 실행 완료 후 Snapshot을 저장한다.

반드시 유지할 핵심 데이터:

1. 지난주 TOP 5
2. 이전 화제성 점수
3. 이전 Star 수
4. 이전에 소개한 프로젝트
5. 다음 주 관찰 프로젝트

10.1 지난주 TOP 5 저장

저장:
- 순위
- Repository ID
- Repository 이름
- URL
- 분야
- 화제성 점수
- 등급
- 선정 이유
- 주요 이슈 요약
- Release
- Issue
- Security
- License / API 변화
- 소개 날짜

10.2 이전 화제성 점수

가능하면 TOP 5뿐 아니라 주요 후보군도 저장한다.

저장:
- Repository ID
- 측정 주차
- 화제성 점수
- 등급

10.3 이전 Star

저장:
- Repository ID
- Repository 이름
- 측정 시각
- Star 수

최근 7일 Star 증가량은 가능하면
"현재 Snapshot Star - 이전 Snapshot Star"
방식으로 직접 계산한다.

10.4 이전 소개 프로젝트

저장:
- Repository ID
- 최초 소개 날짜
- 최근 소개 날짜
- 총 소개 횟수
- 최근 순위
- 최근 점수
- 최근 선정 이유

10.5 다음 주 관찰 프로젝트

최대 3개.

저장:
- Repository ID
- 이름
- URL
- 당시 Star
- 당시 점수
- 성장 신호
- 관찰 이유
- 다음 주 확인 조건

10.6 식별 기준

Repository 식별 우선순위:

1. GitHub Repository 고유 ID
2. canonical Repository URL
3. Owner + Repository 이름

10.7 데이터 보관 기간

권장:

- 최근 4주: 상세 Snapshot 유지
- 최근 3개월: 주요 후보·점수 기록 유지
- 그 이전: 소개 이력과 주요 이벤트 최소 유지

11. 중복 및 재선정 처리
======================================================================

이전에 소개한 프로젝트는 단순히 점수가 높다는 이유만으로 반복 소개하지 않는다.

재선정이 가능한 새로운 변화:

- Major Release
- v1.0 정식 출시
- Star 재급증
- Critical / High Security
- License 변경
- 주요 API 변경
- 프로젝트 종료 / 유지보수 중단
- 대규모 Breaking Change
- 새로운 기술적 논쟁
- 개발 생태계에 영향을 줄 사건

재선정 시 반드시:
"지난번 소개 이후 무엇이 달라졌는가"
를 설명한다.

12. 화제성 점수 계산
======================================================================

총점 100점.

- 최근 7일 Star 증가량: 25점
- 최근 7일 Star 증가율: 20점
- GitHub Trending: 15점
- Issue / PR 활동: 15점
- Fork / Discussions: 5점
- 주요 Release: 10점
- 특별 이벤트: 10점

12.1 Star 증가량 - 25점

Repository 규모별 기준 T:

100~499:
T = 50

500~1,999:
T = 100

2,000~9,999:
T = 300

10,000~49,999:
T = 700

50,000 이상:
T = 1,500

점수:

- 기준 미만: 0
- 기준 충족: 10
- 1.5T 이상: 15
- 2T 이상: 20
- 3T 이상: 25

12.2 Star 증가율 - 20점

- 5% 미만: 0
- 5~10% 미만: 4
- 10~20% 미만: 8
- 20~50% 미만: 12
- 50~100% 미만: 16
- 100% 이상: 20

생성 30일 이내 신규 저장소는 최대 16점.

12.3 Trending - 15점

- 미진입: 0
- 30위 이하 / 낮은 노출: 4
- Top 16~30: 8
- Top 6~15: 12
- Top 1~5: 15

정확한 순위가 불가능하고 진입만 확인되는 경우:
- 진입 확인: 10
- 명확한 상위권: 15

12.4 Issue / PR - 15점

절대 활동량 최대 7점:

- 0~4: 0
- 5~9: 2
- 10~29: 4
- 30~99: 6
- 100 이상: 7

전주 대비 증가율 최대 8점:

- 25% 미만: 0
- 25~50% 미만: 2
- 50~100% 미만: 4
- 100~200% 미만: 6
- 200% 이상: 8

12.5 Fork / Discussions - 5점

- 변화 거의 없음: 0
- 소폭 증가: 1
- 관심 증가 확인: 2
- 뚜렷한 증가: 3
- 매우 활발: 4
- 급격한 증가: 5

정확한 수치가 부족할 경우 근거 있는 정성 평가 허용.

12.6 Release - 10점

- 없음 / 단순 Patch: 0
- 의미 있는 Minor: 2
- 주요 기능 추가: 4
- 대규모 성능 개선: 5
- v1.0 정식 출시: 7
- Major Version: 7
- Breaking Change: 8
- 생태계 영향이 매우 큰 Release: 10

여러 조건을 만족해도 가장 높은 점수 하나만 적용한다.

12.7 특별 이벤트 - 10점

- 경미한 정책 / 운영 변화: 2
- 주요 커뮤니티 논란: 5
- 라이선스 변경: 6
- 중요한 API 폐기 / 변경: 6
- 유지보수 중단: 7
- High 보안 취약점: 7
- 프로젝트 종료: 8
- Critical 보안 취약점: 10
- RCE: 10
- Supply-chain Attack: 10

여러 사건이 있어도 기본 점수는 가장 높은 사건 하나만 적용한다.

12.8 등급

- 85~100: 핵심 이슈
- 70~84: 매우 화제
- 55~69: 주목할 만함
- 40~54: 관찰 대상
- 0~39: 낮은 우선순위

13. TOP 5 최종 선정
======================================================================

기본 절차:

1. 후보 점수 계산
2. 점수순 임시 순위 생성
3. 동일 프로젝트 중복 사건 탐지
4. 동일 프로젝트 사건 통합
5. 더 높은 순위를 대표 순위로 유지
6. 빈 순위는 다음 후보로 승격
7. Critical 보안 이슈 포함 여부 확인
8. 미포함 Critical 이슈 강제 포함
9. 분야 편중은 인위적으로 조정하지 않음
10. 서로 다른 프로젝트 기준 최종 TOP 5 확정

13.1 동일 프로젝트 다중 사건

예:
A 프로젝트 / 사건 ㄱ = TOP 3
A 프로젝트 / 사건 ㄴ = TOP 5

처리:
- A 프로젝트를 하나로 통합
- TOP 3 유지
- 사건 ㄱ과 ㄴ을 모두 TOP 3 내용에 포함
- 두 사건의 관계와 각각의 영향 설명
- 개발자 반응도 사건별 차이가 있으면 설명

점수는 단순 합산하지 않는다.
가장 높은 대표 점수를 유지한다.

13.2 동일 분야 편중

TOP 5가 전부 같은 분야여도 그대로 유지한다.

분야 다양성을 위해 낮은 순위 프로젝트를 억지로 끼워 넣지 않는다.
특정 분야가 TOP 5를 독점했다면 그것 자체를 주간 트렌드로 해석한다.

13.3 Critical 보안

Critical Security Issue는 TOP 5 안에 반드시 포함한다.

무조건 TOP 1로 올리지는 않는다.
순위 결정 시:

- 프로젝트 규모
- 영향 사용자 범위
- 공격 가능성
- 실제 악용 여부
- 패치 여부
- 생태계 영향
- 화제성 점수
- 긴급성

을 함께 본다.

TOP 5에 이미 포함되어 있다면 별도 중복 항목을 만들지 않는다.

14. 최소 근거 및 데이터 부족 처리
======================================================================

14.1 절대 원칙

- 임의 추정 금지
- 확인할 수 없는 수치 생성 금지
- 실제 0과 "미확인"을 구분
- 일부 데이터가 없어도 다른 정상 신호로 평가
- 근거가 지나치게 부족하면 후보 제외

14.2 미확인 표기

사용 가능한 표현:

- 정확한 수치 확인 어려움
- 데이터 확인 불가
- 해당 기간 데이터 미확보
- 비교 데이터 부족
- 확인 가능한 근거 없음

14.3 점수 처리

- 확인 가능: 정상 점수
- 확인 불가: 미평가 / 계산 제외
- 다른 지표: 정상 계산

내부 저장 시:
"0점"과 "미확인"을 별도 상태로 보관한다.

14.4 최소 근거

일반 후보는 다음 중 최소 2개 이상의 독립적 신호를 권장한다.

- Star 급증
- Trending
- Issue / PR 증가
- Major Release
- 활발한 Discussion
- Security
- License / API 변화

예외:
Critical Security처럼 단일 사건 자체가 충분히 강하면 1개 근거로도 유지 가능.

14.5 후보 제외

다음과 같이 GitHub 내부에서 화제성을 판단할 근거가 거의 없으면 제외한다.

- Star 변화 확인 불가
- Trending 확인 불가
- Issue / PR 확인 불가
- 중요한 Release 없음
- 커뮤니티 논의 없음
- 특별 이벤트 없음
- 외부 자료만 존재

14.6 수집 경로 일부 실패

Trending 수집이 실패해도
조건 검색 / Issue / Release가 정상이라면 분석 계속.

전체 Repository 조회 등 핵심 데이터 소스가 광범위하게 실패해
신뢰 가능한 TOP 5 선정이 불가능하면
억지로 TOP 5를 생성하지 않는다.

15. 서술형 콘텐츠 생성
======================================================================

15.1 근거 우선순위

1. Repository README / 공식 문서
2. Release Notes / Changelog
3. Issues
4. Discussions
5. Pull Request
6. Security Advisory

외부 기사 / 블로그 / SNS는 보조 자료.

15.2 사실과 의견 분리

사실 예:
- Release 발생
- 기능 추가
- Star 증가
- Issue 생성
- 버그 확인
- 영향 버전

의견 예:
- 사용하기 쉽다는 평가
- 기존 도구보다 낫다는 주장
- Production 적용이 이르다는 우려

사실과 의견을 섞어 단정하지 않는다.

15.3 "왜 화제가 되었나"

반드시 다음 구조를 따른다.

1. 배경
2. 직접적인 계기
3. 관심 증가
4. 반응 이유

단순히 "Star가 증가해서 화제"라고 끝내지 않는다.

가능하면:
- 어떤 Release / 기능 / 사건이 계기였는지
- 기존 기술과 무엇이 다른지
- 왜 개발자들이 공유하거나 테스트하는지
- 기술적 이유인지 일시적 유행인지

를 구체적으로 설명한다.

필요하면 여러 문단으로 충분히 작성한다.

15.4 "무엇을 하는 프로젝트인가"

포함:
- 목적
- 주요 기능
- 핵심 기술 구조
- 사용 대상
- 유사 기술과 차이
- 이번 업데이트의 변화

15.5 "개발자에게 왜 중요한가"

핵심 질문:
"이 변화 때문에 실제 개발자의 작업 방식이 어떻게 달라질 수 있는가?"

관점:
- 생산성
- 비용
- 성능
- 안정성
- 보안
- 유지보수
- 학습 난이도
- 배포
- 인프라
- API
- 기존 기술 대체 가능성
- 생태계 영향

15.6 "개발자들은 무엇을 이야기하고 있나"

의견은 다음 세 그룹으로 나눈다.

A. 긍정적인 의견
B. 우려하거나 비판하는 의견
C. 논쟁 중인 부분

개별 댓글을 나열하지 않고
반복되는 의견 패턴을 요약한다.

15.7 의견 일반화 강도

여러 Issue / Discussion에서 반복:
- "여러 개발자들이..."
- "반복적으로 제기되는 의견은..."

한 Discussion에서 다수:
- "해당 Discussion에서는..."

소수 의견:
- "일부 개발자는..."
- "몇몇 사용자는..."

댓글 1~2개:
- "한 사용자 또는 일부 사용자가..."

근거가 부족하면:
- "대부분의 개발자"
- "커뮤니티 전체"
와 같은 표현 금지.

15.8 "주의할 점"

실제 근거가 있을 때만 작성한다.

가능한 근거:
- Experimental / Beta
- 반복 버그
- Production 안정성 부족
- API 변경 가능성
- Breaking Change
- 라이선스 제한
- Security Advisory
- 플랫폼 호환성
- 성능 검증 부족
- 유지보수 저하
- 문서 부족

특별한 문제가 없으면 억지로 작성하지 않는다.

18. Telegram 전송 운영
======================================================================

18.1 전송 순서

1. 주간 요약
2. TOP 1
3. TOP 2
4. TOP 3
5. TOP 4
6. TOP 5
7. 특별 경고
8. 주간 전체 트렌드 / 다음 주 관찰

18.2 실패 처리

각 메시지는 독립적으로 처리한다.

- 최초 전송 1회
- 실패 시 1차 재시도
- 실패 시 2차 재시도
- 총 최대 3회

3회 모두 실패하면:
- 해당 메시지 포기
- 다음 메시지는 계속 전송
- 다음 주에 재전송하지 않음
- 다음 주 리포트에 합쳐 보내지 않음

18.3 긴 메시지 분할

메시지가 너무 길면 섹션 단위로 분할한다.

기본:

TOP N (1/2)
- 프로젝트명
- 분야
- 점수
- 주요 지표
- 왜 화제가 되었나
- 무엇을 하는 프로젝트인가

TOP N (2/2)
- 개발자에게 왜 중요한가
- 커뮤니티 의견
- 주의할 점
- 링크

문장 중간 / 문단 중간에서 자르지 않는다.
같은 TOP 항목의 분할 메시지는 연속 전송한다.

필요하면 3개 이상으로 분할 가능하지만
불필요하게 잘게 나누지 않는다.

18.4 링크 미리보기

기본 OFF.

링크는 텍스트 링크 형태로 제공한다.

18.5 특별 경고

Critical 보안 등의 사건은:
- TOP 5 안에서 상세 설명
- 별도 특별 경고 메시지 추가 가능

특별 경고는 TOP 5 이후, 주간 전체 트렌드 이전에 전송한다.

18.6 전송 간격

가능하면 메시지 사이 1~3초의 짧은 간격을 둔다.

재시도도 즉시 폭주하지 않고 짧은 간격을 둘 수 있다.

18.7 전송 로그

기록 권장:

- 실행 날짜
- 메시지 종류
- TOP 순위
- 분할 번호
- 최초 전송 결과
- 1차 재시도 결과
- 2차 재시도 결과
- 최종 상태

상태:

- 성공
- 재시도 후 성공
- 최종 실패


======================================================================
19. 후보 압축과 토큰 효율
======================================================================

운영 효율을 위해 초기 후보 전체를 깊게 읽지 않는다.

권장 파이프라인:

[1단계]
후보 약 30~50개
→ 기본 정량 데이터 중심 수집

[2단계]
화제성 점수 계산
→ 상위 약 8~10개 유지

[3단계]
상위 후보의 Release / 주요 Issue 간단 검증

[4단계]
최종 TOP 5 선정

[5단계]
TOP 5만 README / Issue / Discussion / PR 심층 분석

[6단계]
Telegram 장문 메시지 생성

초기 후보 30~50개 모두에 대해
모든 Issue / Discussion / PR을 읽지 않는다.


======================================================================
20. 검증 및 테스트
======================================================================

실제 운영 전에 다음 4단계 테스트를 진행한다.

20.1 1단계 - 저비용 구조 테스트

- 후보 약 10개
- 장문 콘텐츠 생성 없음
- 점수 계산 / 중복 처리 / Critical 예외 / Snapshot 비교 검증

확인:

- 후보 과다 / 부족
- 유명 프로젝트 편중
- 점수 분포 이상
- 중복 통합 정상 여부
- Critical 포함 정상 여부

20.2 2단계 - TOP 5 서술 테스트

1단계 데이터 재사용.

TOP 5만 심층 분석.

테스트 제한:

프로젝트당:
- 주요 Issue 최대 3
- Discussion 최대 2
- PR 최대 2
- 핵심 Release 최대 1~2

확인:

- 화제 이유가 구체적인가
- README 홍보 문구를 반복하지 않는가
- 개발자 영향 설명이 실질적인가
- 의견 일반화가 과장되지 않는가
- 주의사항이 실제 근거에 기반하는가

20.3 3단계 - Telegram 출력 테스트

GitHub 재검색 금지.
2단계 결과 재사용.

확인:

- 메시지 길이
- 모바일 가독성
- 이모지 과다 여부
- 링크 과다 여부
- 분할 정상 여부
- 섹션 구조 일관성

20.4 4단계 - 최종 전체 통합 테스트

실제 운영과 동일하게 1회 실행.

확인:

- 후보 수집 품질
- TOP 5 타당성
- 점수 분포
- 중복 처리
- Critical 포함
- 서술 품질
- Telegram 품질
- 데이터 실패 처리

전체 통합 테스트는 반복하지 않고
문제가 생긴 단계만 재테스트한다.

20.5 운영 초기 모니터링

초기 3~4주간 관찰:

- 특정 프로젝트 반복 등장
- 특정 분야 편중
- 점수 이상
- Watchlist 유용성
- 커뮤니티 의견 품질
- Telegram 길이
- 데이터 수집 실패 빈도

필요 시 한 번에 많은 규칙을 바꾸지 않고
1~2개 기준만 조정한다.

22. 최종 품질 체크리스트
======================================================================

[데이터]
- 조사 기간이 정확히 168시간인가
- 이전 Snapshot과 올바르게 매칭되었는가
- Repository ID가 동일 프로젝트 추적에 사용되었는가
- 확인 불가 수치를 추정하지 않았는가

[화제성]
- 총 Star 수가 아닌 최근 변화가 반영되었는가
- 대형 / 소형 프로젝트 기준이 구분되었는가
- 신규 Repository 보정이 적용되었는가
- Release / Security / Policy 변화가 반영되었는가

[TOP 5]
- 동일 프로젝트가 중복되지 않았는가
- 다중 사건이 하나의 항목에 통합되었는가
- 빈 순위가 다음 후보로 채워졌는가
- 분야 다양성을 억지로 맞추지 않았는가
- Critical Security가 빠지지 않았는가

[서술]
- "왜 화제인가"에 직접 계기가 있는가
- 사실과 의견이 분리되었는가
- 커뮤니티 의견이 실제 근거에 기반하는가
- 소수 의견을 전체 의견으로 일반화하지 않았는가
- 개발자에게 중요한 이유가 기능 소개와 구분되는가
- 주의사항을 억지로 만들지 않았는가

[Telegram]
- 주간 요약 → TOP 1~5 → 특별 경고 → 주간 정리 순서인가
- 메시지가 지나치게 길면 섹션 단위로 분할되었는가
- 링크 미리보기가 꺼져 있는가
- 실패 메시지만 재시도하는가
- 2회 재시도 후 실패 시 다음 메시지로 진행하는가

[운영]
- 전송 로그가 남았는가
- 이번 주 Snapshot이 저장되었는가
- 소개 이력이 갱신되었는가
- Watchlist가 저장되었는가

23. 절대 금지 사항
======================================================================

- 확인되지 않은 Star 증가량 생성
- Trending 순위 추정
- 댓글 수 추정
- 존재하지 않는 Release / Security 사건 생성
- 외부 기사만 보고 GitHub 사건을 사실로 확정
- 소수 의견을 전체 개발자 의견으로 일반화
- 밈성 프로젝트를 단순 인기만으로 TOP 5에 선정
- 동일 Repository를 여러 TOP 순위로 중복 선정
- 분야 다양성을 위해 점수가 낮은 후보를 억지로 승격
- Critical Security 사건을 일반 점수만으로 탈락
- 데이터가 광범위하게 실패했는데 억지로 TOP 5 생성
- 전송 실패한 메시지를 다음 주에 자동 재발송
