# Telegram 주간 GitHub AI·개발 이슈 전송 운영 규칙

## 1. 목적

GitHub 주간 리포트를 Telegram으로 안정적이고 읽기 좋은 형태로 전송하기 위한 운영 기준을 정의한다.

핵심 목표:
- 메시지 순서를 일정하게 유지
- 일부 전송 실패가 전체 리포트를 중단시키지 않도록 처리
- 긴 메시지는 읽기 좋은 단위로 분할
- 링크 미리보기로 인한 가독성 저하 방지
- Critical 보안 및 특별 사건을 별도 경고로 강조
- 실패 이력을 내부적으로 추적

---

## 2. 기본 전송 순서

매주 생성된 리포트는 다음 순서로 전송한다.

1. 주간 요약
2. TOP 1
3. TOP 2
4. TOP 3
5. TOP 4
6. TOP 5
7. 특별 경고 — 해당 주에 존재하는 경우만
8. 주간 전체 트렌드 및 다음 주 관찰 프로젝트

이 순서를 기본 구조로 유지한다.

---

## 3. 주간 요약 메시지

가장 먼저 발송한다.

포함 내용:
- 조사 기간
- 이번 주 TOP 5 개수
- 핵심 트렌드
- 최고 화제성 프로젝트
- 전체 보고서의 간단한 안내

목적:
사용자가 세부 내용을 읽기 전에 이번 주 전체 흐름을 빠르게 파악할 수 있도록 한다.

---

## 4. TOP 5 메시지 전송

TOP 1부터 TOP 5까지 순서대로 발송한다.

각 TOP 항목은 서로 독립된 메시지로 취급한다.

기본 순서:

TOP 1
→ TOP 2
→ TOP 3
→ TOP 4
→ TOP 5

TOP 5는 사전에 확정한 상세 Telegram 메시지 형식을 사용한다.

---

## 5. 메시지별 실패 처리

각 메시지 전송은 독립적으로 처리한다.

기본 정책:

- 최초 전송: 1회
- 실패 시 재시도: 최대 2회
- 최대 총 시도 횟수: 3회

처리 흐름:

최초 전송
→ 실패
→ 1차 재시도
→ 실패
→ 2차 재시도
→ 실패
→ 해당 메시지 전송 포기

---

## 6. 일부 메시지 실패 시 처리

하나의 메시지가 최종적으로 전송 실패해도
전체 주간 리포트 발송을 중단하지 않는다.

예:

TOP 1 → 성공  
TOP 2 → 성공  
TOP 3 → 최종 실패  
TOP 4 → 계속 전송  
TOP 5 → 계속 전송

즉, 하나의 메시지 실패가 이후 메시지에 영향을 주지 않도록 한다.

---

## 7. 실패한 메시지 재전송 정책

최대 2회의 재시도 후에도 실패한 메시지는 해당 주에 더 이상 전송하지 않는다.

또한:

- 다음 주에 자동 재전송하지 않는다.
- 다음 주 리포트에 실패한 메시지를 합쳐 보내지 않는다.
- 동일한 보고서를 반복 발송하지 않는다.

전송 실패는 해당 주의 전송 문제로만 처리한다.

---

## 8. 긴 메시지 분할 규칙

TOP 5 각각의 서술형 내용이 길어질 경우 하나의 메시지로 억지로 압축하지 않는다.

메시지가 지나치게 길 경우 섹션 단위로 분할한다.

권장 방식:

### 첫 번째 메시지

TOP N — Project A (1/2)

포함:
- 프로젝트명
- 분야
- 화제성 점수
- 주요 지표
- 왜 화제가 되었나
- 무엇을 하는 프로젝트인가

### 두 번째 메시지

TOP N — Project A (2/2)

포함:
- 개발자에게 왜 중요한가
- 개발자들은 무엇을 이야기하고 있나
- 주의할 점
- 관련 링크

---

## 9. 메시지 분할 원칙

메시지는 다음 기준으로 나눈다.

- 문장 중간에서 자르지 않는다.
- 문단 중간에서 자르지 않는다.
- 가능한 한 섹션 단위로 자른다.
- 같은 TOP 항목의 메시지는 연속해서 보낸다.

예:

TOP 2 (1/2)
→ TOP 2 (2/2)
→ TOP 3

TOP 2 (1/2)
→ TOP 3
→ TOP 2 (2/2)

처럼 순서를 섞지 않는다.

---

## 10. 메시지 분할 개수

기본적으로:

- 1개 메시지
또는
- 2개 메시지

로 처리한다.

내용이 매우 길어 2개로도 부족한 경우에는 3개 이상으로 나눌 수 있다.

단, 불필요하게 잘게 나누지는 않는다.

가독성과 문맥 유지가 우선이다.

---

## 11. 분할 메시지 실패 처리

TOP 항목이 여러 메시지로 나누어진 경우
각 분할 메시지를 독립적인 전송 단위로 취급한다.

예:

TOP 1 (1/2) → 성공  
TOP 1 (2/2) → 실패

TOP 1 (2/2)만 최대 2회 재시도한다.

최종 실패하더라도 TOP 2 전송은 계속한다.

---

## 12. 링크 미리보기

GitHub 링크의 Telegram 미리보기는 기본적으로 사용하지 않는다.

기본 설정:

링크 미리보기 OFF

이유:
- Repository 링크가 여러 개 존재
- Issue / Discussion 링크가 다수 존재할 수 있음
- 링크 카드가 메시지보다 많은 공간을 차지할 수 있음
- 전체 리포트 스크롤 길이가 지나치게 증가
- 텍스트 중심의 주간 보고서 가독성을 유지하기 위함

---

## 13. 링크 표시 방식

링크는 텍스트 형태로 제공한다.

예:

GitHub  
https://github.com/...

주요 Issue  
https://github.com/...

Discussion  
https://github.com/...

Release  
https://github.com/...

필요한 링크만 포함하며
관련성이 낮은 링크를 과도하게 나열하지 않는다.

---

## 14. 특별 경고 메시지

다음과 같은 특별 사건은 별도 Telegram 메시지로 추가 발송한다.

대표적인 대상:

- Critical Security Vulnerability
- Remote Code Execution
- Supply-chain Attack
- Authentication Bypass
- 대규모 Credential Exposure
- 중요한 라이선스 변경
- 프로젝트 종료
- 광범위한 Breaking Change
- 개발 생태계에 큰 영향을 줄 긴급 사건

---

## 15. 특별 경고와 TOP 5의 관계

Critical 보안 등의 사건은 TOP 5 내부에도 포함한다.

즉:

TOP 5 상세 리포트에서 해당 사건 설명
+
별도의 특별 경고 메시지 추가

두 방식을 함께 사용한다.

특별 경고 메시지는 TOP 5 내용을 완전히 반복하지 않는다.

별도 메시지에서는 다음 내용을 중심으로 간결하게 작성한다.

- 무슨 사건인지
- 영향 범위
- 영향을 받는 버전
- 긴급성
- 권장 대응
- 관련 공식 링크

---

## 16. 특별 경고 발송 위치

특별 경고 메시지는 기본적으로 TOP 5 발송 이후에 전송한다.

기본 순서:

주간 요약
→ TOP 1
→ TOP 2
→ TOP 3
→ TOP 4
→ TOP 5
→ 특별 경고
→ 주간 전체 트렌드

긴급성을 지나치게 강조해 전체 순서를 변경하지 않고,
보고서 구조를 일정하게 유지한다.

---

## 17. 메시지 간 전송 간격

가능하다면 각 Telegram 메시지 사이에 짧은 전송 간격을 둔다.

권장:
- 약 1~3초

목적:
- Telegram API 연속 요청 부담 완화
- rate limit 가능성 감소
- 안정적인 순차 전송
- 메시지 순서 꼬임 방지

실제 구현 환경에서 필요하면 조정할 수 있다.

---

## 18. 재시도 간격

메시지 전송 실패 후 즉시 반복 요청하기보다 짧은 간격을 둘 수 있다.

권장 흐름:

전송 실패
→ 짧은 대기
→ 1차 재시도
→ 실패
→ 짧은 대기
→ 2차 재시도

정확한 대기 시간은 실제 Telegram Bot 구현 시 조정한다.

---

## 19. 전송 실패 로그

Telegram 전송 결과를 내부적으로 기록하는 것을 권장한다.

저장 가능한 항목:

- 실행 날짜
- 메시지 종류
- TOP 순위
- 분할 번호
- 최초 전송 성공 / 실패
- 1차 재시도 결과
- 2차 재시도 결과
- 최종 상태

예:

2026.10.11  
TOP 3 (1/2)  
최초 실패  
1차 재시도 실패  
2차 재시도 실패  
최종 상태: 전송 실패

---

## 20. 전송 성공 상태

각 메시지는 다음 상태 중 하나로 관리할 수 있다.

- 성공
- 재시도 후 성공
- 최종 실패

이를 통해 자동화가 정상적으로 동작했는지 확인할 수 있다.

---

## 21. 마지막 주간 정리 메시지

모든 TOP 5와 특별 경고 발송이 끝난 후
마지막으로 주간 전체 트렌드 메시지를 발송한다.

포함 내용:

- 이번 주 GitHub 전체 기술 흐름
- TOP 5 공통 패턴
- 다음 주 관찰 프로젝트
- 이번 주 한 줄 정리
- 데이터 신뢰성 안내

일부 TOP 메시지가 실패했더라도 마지막 정리 메시지는 정상적으로 발송한다.

---

## 22. 최종 전송 흐름

주간 보고서 생성 완료
        ↓
주간 요약 전송
        ↓
TOP 1 전송
        ↓
TOP 2 전송
        ↓
TOP 3 전송
        ↓
TOP 4 전송
        ↓
TOP 5 전송
        ↓
특별 경고 존재 여부 확인
        ↓
존재하면 특별 경고 전송
        ↓
주간 전체 트렌드 전송
        ↓
전송 결과 로그 저장

각 메시지:

전송
→ 성공: 다음 메시지
→ 실패: 1차 재시도
→ 실패: 2차 재시도
→ 실패: 최종 실패 기록
→ 다음 메시지 계속

---

## 23. 핵심 운영 원칙

1. 메시지는 정해진 순서대로 발송한다.
2. TOP 5는 각각 독립적인 메시지로 관리한다.
3. 너무 긴 메시지는 섹션 단위로 분할한다.
4. 분할 메시지는 연속해서 발송한다.
5. 각 메시지는 최대 총 3회까지 전송을 시도한다.
6. 하나의 메시지 실패가 전체 리포트를 중단시키지 않는다.
7. 링크 미리보기는 기본적으로 끈다.
8. Critical 보안 등의 특별 사건은 TOP 5에 포함하면서 별도 경고도 전송한다.
9. 메시지 사이에는 가능하면 짧은 간격을 둔다.
10. 전송 성공 및 실패 결과를 내부적으로 기록한다.
