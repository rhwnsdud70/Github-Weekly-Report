GitHub 주간 AI·개발 이슈 데이터 수집 규칙 - 최종본

목적
매주 최근 7일 동안 GitHub에서 화제가 된 AI 및 소프트웨어 개발 관련 프로젝트, 저장소, Issue, Release, 보안 사건을 체계적으로 수집하기 위한 최종 기준을 정의한다.

이 규칙의 목적은 단순히 Star 수가 많은 저장소를 찾는 것이 아니라,
"이번 주에 실제로 새롭게 관심이 증가했거나 개발자가 알아둘 가치가 있는 변화"를 찾는 것이다.

==================================================
1. 기본 수집 전략
==================================================

수집 방식은 혼합형으로 운영한다.

권장 비중:
- GitHub Trending 기반 후보: 40%
- GitHub 전체 조건 검색 후보: 40%
- Issue / Release / Security 이벤트 후보: 20%

위 비율은 초기 운영 기준이며,
실제 결과 품질에 따라 추후 조정할 수 있다.

==================================================
2. 수집 기간
==================================================

기본 수집 기간:
- 최근 7일

매주 일요일 실행을 기준으로:
- 직전 월요일부터 해당 일요일까지의 변화를 우선 분석한다.

비교 목적:
- 직전 7일
- 최근 30일

데이터를 보조적으로 참고할 수 있다.

==================================================
4. GitHub Trending 기반 수집
==================================================

목적:
이미 GitHub 커뮤니티에서 큰 관심을 받고 있는 프로젝트를 빠르게 발견한다.

수집 조건:
- 최근 7일 동안 GitHub Trending에 등장
- AI 또는 소프트웨어 개발 관련 프로젝트
- 단순 밈성 프로젝트가 아닐 것

Trending 진입은 그 자체로 후보 등록 조건으로 인정한다.

가능한 경우 Trending 위치를 다음처럼 평가한다.

- Top 1~5: 매우 강한 신호
- Top 6~15: 강한 신호
- Top 16~30: 보통 신호
- 30위 이하: 보조 신호

수집 정보:
- Repository 이름
- Owner
- URL
- 설명
- 주요 언어
- 현재 Star 수
- Fork 수
- 최근 업데이트 날짜
- 최근 Release 여부
- Trending 등장 여부 및 가능하면 위치

주의:
총 Star 수만으로 화제성을 판단하지 않는다.

==================================================
5. GitHub 전체 조건 검색
==================================================

목적:
Trending에 아직 등장하지 않았지만 빠르게 성장하거나 최근 활동이 급증한 프로젝트를 찾는다.

--------------------------------------------------
5-1. 기본 후보 조건
--------------------------------------------------

기본적으로 다음 조건을 사용한다.

현재 Star:
- 최소 100 이상

최근 업데이트:
- 최근 14일 이내를 우선

그리고 아래 조건 중 하나 이상을 만족하면 후보로 등록할 수 있다.

- 최근 7일 Star 증가량 기준 충족
- 최근 7일 Star 증가율 기준 충족
- GitHub Trending 진입
- Issue / PR 활동 급증
- Major Release 발생
- 중요 Security 이슈 발생
- 중요 License / API / Policy 변화 발생

즉, 모든 조건을 AND로 묶지 않고
"기본 관련성 + 하나 이상의 강한 신호" 방식으로 판단한다.

--------------------------------------------------
5-2. 저장소 규모별 Star 증가 임계값
--------------------------------------------------

저장소 규모에 따라 다음 기준을 적용한다.

현재 Star 100~499:
- 최근 7일 +50 이상
또는
- 최근 7일 +25% 이상

현재 Star 500~1,999:
- 최근 7일 +100 이상
또는
- 최근 7일 +20% 이상

현재 Star 2,000~9,999:
- 최근 7일 +300 이상
또는
- 최근 7일 +10% 이상

현재 Star 10,000~49,999:
- 최근 7일 +700 이상
또는
- 최근 7일 +5% 이상

현재 Star 50,000 이상:
- 최근 7일 +1,500 이상
또는
- 최근 7일 +2% 이상

원칙:
- 절대 증가량과 증가율을 동시에 본다.
- 오래된 대형 프로젝트가 단순히 규모가 크다는 이유만으로 우선 선정되지 않도록 한다.

--------------------------------------------------
5-3. 신규 저장소 기준
--------------------------------------------------

신규 프로젝트는 별도 기준을 적용한다.

생성 30일 이내:
- Star 300 이상이면 후보

생성 14일 이내:
- Star 500 이상이면 강한 신흥 후보

생성 7일 이내:
- Star 1,000 이상이면 거의 반드시 검토

신규 저장소는 증가율이 과도하게 크게 계산될 수 있으므로
절대 Star 수와 성장 속도를 함께 본다.

==================================================
6. 활동량 임계값
==================================================

--------------------------------------------------
6-1. Issue
--------------------------------------------------

최근 7일 신규 Issue:
- 10개 이상이면 활동 증가 후보

특정 Issue 댓글:
- 20개 이상: 관심 증가
- 50개 이상: 높은 관심
- 100개 이상: 강한 화제성

다음 유형의 Issue는 숫자 기준을 낮춰도 된다.

- Security
- Breaking Change
- License
- Deprecation
- Major Bug
- Performance
- Project Direction Change

--------------------------------------------------
6-2. Pull Request
--------------------------------------------------

최근 7일 PR:
- 10개 이상: 활발
- 30개 이상: 매우 활발

대형 프로젝트는 평소에도 PR 수가 많을 수 있으므로
절대 수치보다 이전 주 대비 증가율을 더 중요하게 본다.

예:
지난주 PR 12개
이번주 PR 38개
→ 강한 활동 증가 신호

--------------------------------------------------
6-3. 활동 급증률
--------------------------------------------------

Star, Issue, PR, Discussion 등에 공통 적용할 수 있다.

- +25%: 관심 증가
- +50%: 뚜렷한 증가
- +100%: 강한 상승
- +200% 이상: 급격한 화제성

==================================================
7. Release 수집 규칙
==================================================

모든 Release를 수집하지 않는다.

다음 유형은 우선 후보로 등록한다.

- v1.0 또는 정식 버전 출시
- Major Version Release
- Breaking Change
- 신규 AI 모델 지원
- 신규 API
- 아키텍처 변경
- 대규모 성능 개선
- 주요 기능 추가
- Migration이 필요한 변경
- 기존 기능 Deprecation 또는 제거

단순한 Patch Release나 경미한 버그 수정은 기본적으로 제외한다.

==================================================
8. Security 이벤트 규칙
==================================================

다음 보안 사건은 Star 증가량과 무관하게 반드시 검토한다.

- Critical Severity
- Remote Code Execution
- Authentication Bypass
- Privilege Escalation
- Supply-chain Attack
- Credential Exposure
- Widely-used Dependency Vulnerability
- 광범위하게 영향을 주는 High Severity 취약점

보안 사건은 저장소 인기와 별개로
개발 생태계 영향도가 높으면 최종 보고서 후보에 포함할 수 있다.

==================================================
9. License / API / Project Policy 이벤트
==================================================

다음 사건은 일반 인기 기준과 별도로 중요 후보로 취급한다.

- 라이선스 변경
- 오픈소스에서 상업용 제한으로 변경
- API 폐기
- 주요 기능 제거
- 프로젝트 유지보수 중단
- 프로젝트 종료
- 프로젝트 소유권 변경
- 주요 Governance 변경
- 대규모 커뮤니티 논란
- 프로젝트 방향성 변경

==================================================
10. 후보 등록 최종 조건
==================================================

Repository 또는 사건이 다음 조건을 만족하면 후보로 등록할 수 있다.

[필수]
AI 또는 소프트웨어 개발 관련성이 있을 것

그리고 아래 조건 중 하나 이상:

1. GitHub Trending 진입

2. 최근 7일 Star 증가량 기준 충족

3. 최근 7일 Star 증가율 기준 충족

4. 생성 30일 이하 + Star 300 이상

5. 특정 Issue 댓글 50개 이상

6. Issue / PR 활동이 이전 주 대비 100% 이상 증가

7. Major Release 발생

8. Critical / High Security 이슈 발생

9. 중요한 License / API / Project Policy 변화 발생

10. 프로젝트 종료, 유지보수 중단, 대형 버그 등 개발 생태계에 영향이 큰 사건 발생

==================================================
11. 수집 데이터 필드
==================================================

각 후보에서 가능한 범위 내 다음 정보를 수집한다.

[기본 정보]
- Repository 이름
- Owner
- GitHub URL
- 프로젝트 설명
- 주요 분야
- 주요 언어
- 현재 Star 수
- 현재 Fork 수
- 생성일
- 최근 업데이트일

[화제성 정보]
- 최근 7일 Star 증가량
- 최근 7일 Star 증가율
- 최근 Fork 증가 여부
- Trending 여부
- Trending 위치
- 최근 Issue 수
- 최근 PR 수
- 최근 Discussion 활동
- 이전 주 대비 활동 증가율

[이벤트 정보]
- 주요 Issue
- Issue 댓글 및 반응
- 주요 Release
- Breaking Change
- Security 이슈
- License 변경
- API 변경
- 유지보수 중단 여부

[분석용 정보]
- 수집 경로
- 화제가 된 직접적인 이유
- 개발자에게 미칠 영향
- 이전 주 보고서 등장 여부

==================================================
12. 후보 통합 및 중복 제거
==================================================

세 경로에서 수집한 후보를 하나로 통합한다.

순서:
1. GitHub Trending 후보 수집
2. GitHub 전체 조건 검색 후보 수집
3. Issue / Release / Security 후보 수집
4. Repository 기준 중복 제거
5. 동일 프로젝트의 여러 사건을 필요하면 하나로 통합
6. 프로젝트와 사건의 중요도를 함께 기록
7. 화제성 점수 계산 단계로 전달

동일 Repository가 여러 경로에서 발견되면 하나로 합친다.

예:
- Trending 진입
- Star 급증
- Major Release 발생

→ 하나의 후보로 통합하고 모든 신호를 함께 기록

==================================================
13. 이전 주 중복 방지
==================================================

이전 주 보고서에 포함된 프로젝트라고 해서 자동 제외하지 않는다.

다만 다음과 같은 새로운 변화가 없는 경우 반복 소개하지 않는다.

재선정 허용 조건:
- 신규 대규모 Release
- Star 재급증
- 중요 보안 이슈
- 라이선스 변경
- API 변경
- 프로젝트 종료
- 주요 기능 공개
- 중요한 논란 발생

반복 소개하는 경우:
- 이전 주와 무엇이 달라졌는지 반드시 설명한다.

==================================================
14. 후보 수 관리
==================================================

초기 수집 후보 권장 범위:

- Trending 기반: 약 10~20개
- 전체 조건 검색: 약 10~30개
- Issue / Release / Security: 약 5~15개

이후 다음 단계를 거친다.

- 중복 제거
- 관련성 필터
- 화제성 평가
- 뉴스 가치 평가
- 최종 선정

최종 보고서:
- 약 5~10개

중요한 이슈가 적으면 억지로 개수를 채우지 않는다.

==================================================
15. 데이터 정확성 원칙
==================================================

확인할 수 없는 수치를 임의로 생성하지 않는다.

정확한 최근 7일 Star 증가량을 확인할 수 없는 경우:
- "정확한 증가량 확인 어려움"
- "최근 급증 확인"

등으로 표시한다.

추정치를 사용할 경우:
- 반드시 추정임을 명시한다.

원본 정보 우선순위:
1. GitHub Repository
2. GitHub Issue
3. GitHub Pull Request
4. GitHub Release
5. GitHub Discussions
6. 공식 프로젝트 문서

외부 기사, 블로그, SNS는 보조 자료로만 사용한다.

17. 핵심 원칙
==================================================

- 총 Star 수보다 최근 7일간 변화량을 더 중요하게 본다.
- 절대 증가량과 증가율을 함께 본다.
- 대형 프로젝트와 신생 프로젝트에 동일 기준을 적용하지 않는다.
- 신규 프로젝트는 별도 기준으로 평가한다.
- Trending만 의존하지 않는다.
- Issue, PR, Release, Security 사건도 함께 본다.
- 보안, 라이선스, API, 프로젝트 종료 사건은 인기와 별개로 중요하게 본다.
- 정확하지 않은 수치를 사실처럼 작성하지 않는다.
- 유명하다는 이유만으로 선정하지 않는다.
- 최종 목표는 "이번 주 개발자가 알아둘 가치가 있는 GitHub 변화"를 찾는 것이다.
