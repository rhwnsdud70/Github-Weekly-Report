# GitHub 주간 AI·개발 이슈 검증 및 테스트 규칙

## 1. 목적

자동화를 실제 주간 운영에 투입하기 전에 데이터 수집, 점수 계산, TOP 5 선정, 서술형 콘텐츠 생성, Telegram 메시지 출력이 정상적으로 동작하는지 검증한다.

테스트의 핵심 목표는 다음과 같다.

- 후보가 지나치게 많이 또는 적게 수집되지 않는지 확인
- 유명 프로젝트만 반복적으로 선정되지 않는지 확인
- 화제성 점수가 과도하게 높거나 낮게 계산되지 않는지 확인
- 커뮤니티 의견 요약이 과장되거나 일반화되지 않는지 확인
- Telegram 메시지가 지나치게 길거나 읽기 어렵지 않은지 확인
- 전체 자동화의 토큰 및 처리 비용을 불필요하게 증가시키지 않음

---

# 2. 테스트 기본 원칙

자동화를 처음부터 전체 규모로 여러 번 실행하지 않는다.

테스트는 다음 4단계로 나누어 진행한다.

1. 저비용 구조 테스트
2. TOP 5 서술형 콘텐츠 테스트
3. Telegram 출력 테스트
4. 최종 전체 통합 테스트

전체 GitHub 조사와 장문 콘텐츠 생성을 동시에 수행하는 고비용 테스트는 마지막에 한 번만 실시한다.

---

# 3. 1단계 — 저비용 구조 테스트

## 목적

데이터 수집과 화제성 점수 계산 구조가 정상적으로 동작하는지 검증한다.

## 테스트 범위

실제 GitHub 전체 후보를 모두 조사하지 않는다.

권장:
- 후보 약 10개
- 가능하면 서로 다른 규모와 유형의 프로젝트를 포함

예:
- 대형 유명 Repository
- 최근 급성장한 중형 Repository
- 신규 Repository
- Major Release가 발생한 프로젝트
- Security 사건이 있는 프로젝트

## 이 단계에서 확인할 항목

- 후보 수집 규칙이 정상 적용되는가
- 저장소 규모별 Star 기준이 정상 적용되는가
- Star 증가율 계산이 정상인가
- Trending 점수가 정상인가
- Issue / PR 점수가 정상인가
- Release / 특별 이벤트 점수가 정상인가
- 동일 프로젝트의 중복 사건이 통합되는가
- Critical 보안 이슈가 TOP 5 예외 규칙에 따라 처리되는가
- 이전 주 Snapshot 비교가 정상적으로 가능한가

## 출력 방식

긴 서술형 콘텐츠는 생성하지 않는다.

예:

1. Project A — 88점  
2. Project B — 81점  
3. Project C — 74점  
4. Project D — 66점  
5. Project E — 59점

필요한 경우 각 프로젝트의 세부 점수만 함께 확인한다.

---

# 4. 1단계 검증 기준

다음 문제가 발견되는지 확인한다.

## 후보 과다

너무 많은 Repository가 최소 기준을 통과하는 경우:

- Star 증가 임계값 상향 검토
- 최소 Star 기준 조정
- Issue / PR 활동 조건 강화
- 관련성 필터 강화

## 후보 부족

후보가 지나치게 적은 경우:

- 최소 Star 기준 완화
- Star 증가율 기준 완화
- 신규 프로젝트 기준 조정

## 유명 프로젝트 편중

기존 유명 프로젝트만 상위권을 차지하는 경우:

- 최근 증가율 가중치 점검
- 총 Star 규모가 과도하게 영향을 주는지 확인
- 신규 / 급성장 프로젝트가 정상적으로 점수를 받는지 확인

---

# 5. 2단계 — TOP 5 서술형 콘텐츠 테스트

## 목적

최종 선정된 TOP 5에 대해 서술형 콘텐츠 품질을 검증한다.

## 핵심 원칙

1단계에서 확보한 데이터와 후보를 재사용한다.

새로운 전체 GitHub 검색을 다시 수행하지 않는다.

## 분석 대상

TOP 5 프로젝트만 심층 분석한다.

각 프로젝트에서 확인:

- README
- 주요 Release
- 주요 Issue
- Discussions
- 필요한 PR
- Security Advisory

## 테스트용 수집 제한

토큰 사용량을 줄이기 위해 초기 테스트에서는 다음 정도로 제한한다.

프로젝트당:

- 주요 Issue 최대 3개
- 주요 Discussion 최대 2개
- 주요 PR 최대 2개
- 핵심 Release 최대 1~2개

이 범위 안에서 의미 있는 의견 패턴을 찾는다.

---

# 6. 2단계 검증 항목

각 TOP 5에 대해 확인한다.

## 왜 화제가 되었나

- Star 증가만 반복해서 설명하지 않는가
- 직접적인 계기와 배경이 들어가는가
- Release / 사건 / 기술 변화가 설명되는가
- 관심 증가 이유가 구체적인가

## 프로젝트 설명

- README 홍보 문구를 그대로 복사하지 않는가
- 실제 기능을 이해하기 쉽게 설명하는가
- 기존 기술과의 차이를 과장하지 않는가

## 개발자에게 중요한 이유

- 프로젝트 설명을 반복하지 않는가
- 실제 개발 방식에 미치는 영향을 설명하는가

## 커뮤니티 의견

- 소수 댓글을 전체 의견처럼 일반화하지 않는가
- 긍정 / 우려 / 논쟁을 실제 근거로 나누는가
- 실제 논쟁이 없는데 억지로 찬반 구조를 만들지 않는가

## 주의할 점

- 확인되지 않은 단점을 만들어내지 않는가
- 실제 Issue / 문서 / Security 근거가 있는가

---

# 7. 커뮤니티 의견 과장 검증

특히 다음 표현을 확인한다.

주의 대상:

- "개발자들은 모두..."
- "대부분의 개발자들이..."
- "커뮤니티 전체가..."
- "압도적으로 좋은 평가..."

명확한 근거가 없는 경우 이런 표현을 사용하지 않는다.

대신 다음과 같이 수정한다.

- "여러 Issue에서 반복적으로..."
- "해당 Discussion에서는..."
- "일부 개발자는..."
- "몇몇 사용자는..."

---

# 8. 3단계 — Telegram 출력 테스트

## 목적

이미 생성된 TOP 5 콘텐츠를 실제 Telegram 메시지 형식으로 변환했을 때의 가독성을 검증한다.

## 핵심 원칙

이 단계에서는 GitHub 데이터를 다시 조사하지 않는다.

2단계 결과만 사용한다.

## 확인 항목

- 주간 요약 메시지가 너무 길지 않은가
- TOP 1~5 메시지 구조가 일정한가
- 이모지가 지나치게 많지 않은가
- 구분선이 가독성을 높이는가
- 링크가 너무 많지 않은가
- 각 섹션 제목이 명확한가
- 모바일 화면에서도 읽기 쉬운가
- 하나의 TOP 항목이 지나치게 긴가

---

# 9. Telegram 메시지 길이 검증

TOP 항목이 너무 길 경우 사전에 정한 분할 규칙을 적용한다.

우선:

TOP N (1/2)
- 주요 지표
- 왜 화제가 되었나
- 무엇을 하는 프로젝트인가

TOP N (2/2)
- 개발자에게 왜 중요한가
- 커뮤니티 의견
- 주의할 점
- 링크

원칙:

- 문장 중간 분할 금지
- 문단 중간 분할 금지
- 섹션 단위로 분할
- 같은 TOP 프로젝트의 메시지는 연속해서 배치

---

# 10. 3단계 조정 기준

Telegram 메시지가 지나치게 길 경우:

우선 줄일 것:

- 반복되는 설명
- 중요하지 않은 배경 정보
- 의미가 중복되는 Bullet
- 관련성이 낮은 링크

가능하면 유지할 것:

- 왜 화제가 되었는가
- 개발자에게 중요한 이유
- 커뮤니티 의견
- 주요 위험 요소

즉, 핵심 분석을 줄이기보다 반복과 불필요한 문장을 먼저 제거한다.

---

# 11. 4단계 — 최종 전체 통합 테스트

## 목적

실제 주간 자동화와 동일한 조건으로 전체 파이프라인을 한 번 실행한다.

## 실행 범위

실제 운영과 동일하게:

1. GitHub 후보 수집
2. 데이터 검증
3. 이전 주 데이터 비교
4. 화제성 점수 계산
5. 중복 제거
6. TOP 5 선정
7. 서술형 콘텐츠 생성
8. Telegram 메시지 생성
9. 전송 형식 검증

실제 Telegram 발송은 필요에 따라 테스트 채널 또는 테스트 Bot으로 진행할 수 있다.

---

# 12. 전체 통합 테스트에서 확인할 항목

## 후보 수집

- 후보가 지나치게 많지 않은가
- 지나치게 적지 않은가
- AI Agent 등 특정 분야만 검색 규칙 때문에 과도하게 잡히지 않는가

## TOP 5 품질

- 실제로 그 주에 중요해 보이는 프로젝트인가
- 유명 프로젝트만 반복되지 않는가
- 신규 프로젝트도 적절히 발견되는가
- Critical 보안 사건이 정상 반영되는가

## 점수 분포

- 모든 후보가 80~90점대로 몰리지 않는가
- 대부분이 10~20점에 머물지 않는가
- 후보 간 차이가 적절하게 나타나는가

## 서술 품질

- 사실과 의견이 구분되어 있는가
- 과장 표현이 없는가
- 커뮤니티 의견이 실제 근거를 반영하는가

## Telegram 품질

- 너무 많은 메시지가 생성되지 않는가
- 한 메시지가 지나치게 길지 않은가
- 순서가 정상적인가
- 특별 경고가 정상적으로 분리되는가

---

# 13. 점수 분포 검증

첫 통합 테스트에서는 TOP 5 점수만 보는 것이 아니라 전체 주요 후보의 점수 분포도 확인한다.

예:

후보 20개 중

85점 이상: 1개  
70~84점: 4개  
55~69점: 6개  
40~54점: 5개  
40점 미만: 4개

이런 식으로 어느 정도 분산되는 것이 자연스럽다.

반대로:

20개 중 17개가 80점 이상

또는

20개 중 19개가 40점 미만

이라면 점수 기준을 재검토한다.

단, 특정 주의 실제 상황에 따라 분포가 달라질 수 있으므로 절대적인 비율 기준으로 강제하지 않는다.

---

# 14. 토큰 절감형 실제 운영 구조 검증

테스트 단계에서 다음 구조가 정상 동작하는지 확인한다.

[1단계]
후보 약 30~50개
→ 정량 데이터 중심 수집

        ↓

[2단계]
화제성 점수 계산
→ 상위 약 8~10개만 유지

        ↓

[3단계]
상위 후보의 Release / Issue 간단 검증

        ↓

[4단계]
최종 TOP 5 선정

        ↓

[5단계]
TOP 5만 README / Issue / Discussion / PR 심층 분석

        ↓

[6단계]
Telegram 장문 메시지 생성

이 구조를 실제 운영에서도 기본 비용 절감 전략으로 사용한다.

---

# 15. 불필요한 심층 분석 방지

초기 후보 전체에 대해 다음 작업을 수행하지 않는다.

- 모든 Issue 읽기
- 모든 Discussion 읽기
- 모든 PR 분석
- 모든 README 상세 분석

심층 분석은 TOP 5 선정 이후에만 수행한다.

필요한 경우 최종 선정 직전 상위 8~10개에 대해 최소한의 검증만 실시한다.

---

# 16. 테스트 데이터 재사용

동일한 테스트 과정에서 이미 수집한 데이터를 다시 검색하지 않는다.

원칙:

1단계 데이터
→ 2단계에서 재사용

2단계 콘텐츠
→ 3단계에서 재사용

이를 통해 동일한 GitHub 페이지와 데이터를 반복해서 처리하는 비용을 줄인다.

---

# 17. 테스트 후 수정 우선순위

문제가 발견되면 다음 순서로 수정한다.

1. 데이터 수집 기준
2. 화제성 점수 기준
3. TOP 5 예외 처리
4. 서술형 콘텐츠 규칙
5. Telegram 메시지 길이 및 형식

상위 단계의 문제가 해결되지 않은 상태에서 출력 형식만 수정하지 않는다.

---

# 18. 테스트 완료 조건

다음 조건이 만족되면 실제 주간 운영을 시작할 수 있다.

- 후보 수가 관리 가능한 수준
- 신규 프로젝트와 기존 유명 프로젝트가 균형 있게 발견됨
- 화제성 점수 분포가 비정상적으로 몰리지 않음
- TOP 5 선정 결과가 납득 가능
- 동일 프로젝트 중복 처리가 정상
- Critical 보안 예외 처리가 정상
- 커뮤니티 의견이 실제 근거를 기반으로 작성됨
- 서술형 내용에 명백한 과장이나 추정이 없음
- Telegram 메시지가 읽기 가능한 길이와 구조를 가짐
- 긴 메시지 분할이 정상 작동
- 데이터 부족 시 임의 추정하지 않음

---

# 19. 권장 테스트 횟수

초기 운영 전:

1차 저비용 구조 테스트: 1회  
TOP 5 서술 테스트: 1회  
Telegram 출력 테스트: 1회  
최종 전체 통합 테스트: 1회

필요하면 문제가 발견된 단계만 다시 테스트한다.

전체 통합 테스트를 반복해서 수행하는 것은 기본적으로 피한다.

---

# 20. 운영 시작 후 추가 검증

실제 운영을 시작한 뒤 초기 3~4주 동안 결과 품질을 관찰한다.

확인할 항목:

- 특정 프로젝트의 반복 등장
- 특정 분야 과도한 편중
- 점수 기준 이상 여부
- 관찰 프로젝트의 유용성
- 커뮤니티 반응 분석 품질
- Telegram 메시지 길이
- 데이터 수집 실패 빈도

필요한 경우 한 번에 많은 규칙을 수정하지 않고
한두 개의 기준만 조정하여 결과 변화를 관찰한다.

# 21. 핵심 원칙

1. 전체 자동화를 여러 번 반복 테스트하지 않는다.
2. 테스트는 단계별로 분리한다.
3. 초기 후보 분석은 정량 데이터 중심으로 한다.
4. 심층 분석은 최종 TOP 5에 집중한다.
5. 이미 수집한 데이터는 재사용한다.
6. 커뮤니티 의견 분석 범위를 테스트 단계에서는 제한한다.
7. Telegram 포맷 테스트에서는 GitHub를 다시 조사하지 않는다.
8. 전체 통합 테스트는 마지막에 한 번 수행한다.
9. 문제가 생기면 해당 단계만 다시 테스트한다.
10. 품질과 토큰 효율을 동시에 고려한다.
