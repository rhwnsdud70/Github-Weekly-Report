# GitHub 주간 AI·개발 이슈 TOP 5 최종 예외 처리 규칙

## 1. 동일 프로젝트 중복 사건 처리

동일 Repository 또는 동일 프로젝트에서 여러 사건이 동시에 발생한 경우,
각 사건을 별도의 TOP 항목으로 분리하지 않는다.

예:

- A 프로젝트 / ㄱ사건 → TOP 3
- A 프로젝트 / ㄴ사건 → TOP 5

이 경우 A 프로젝트는 하나의 TOP 항목으로 통합한다.

최종 순위는 더 높은 순위를 유지한다.

위 예시의 경우:

- A 프로젝트 → TOP 3 유지

그리고 TOP 3 메시지 안에 다음 내용을 모두 포함한다.

- ㄱ사건
- ㄴ사건
- 두 사건이 서로 어떤 관련이 있는지
- 각각이 프로젝트 화제성에 어떤 영향을 줬는지
- 개발자 반응이 사건별로 어떻게 달랐는지

즉, 동일 프로젝트에서 발생한 여러 사건은 하나의 종합 이슈로 다룬다.

---

## 2. 중복 통합 후 빈 순위 처리

동일 프로젝트가 여러 순위를 차지해 통합된 경우,
비게 된 순위는 다음 순위 후보가 승격한다.

예:

초기 결과:
1. Project A
2. Project B
3. Project C - 사건 ㄱ
4. Project D
5. Project C - 사건 ㄴ
6. Project E

통합 후:

1. Project A
2. Project B
3. Project C - 사건 ㄱ + 사건 ㄴ
4. Project D
5. Project E

항상 최종적으로 서로 다른 프로젝트 기준 TOP 5를 유지한다.

---

## 3. 동일 프로젝트 내부 화제성 점수 처리

동일 프로젝트의 여러 사건이 각각 별도 점수를 가진 경우,
점수를 단순 합산하지 않는다.

기본 원칙:

- 가장 높은 화제성 점수를 프로젝트의 대표 점수로 사용한다.
- 추가 사건은 대표 점수에 중복 가산하지 않는다.
- 여러 사건이 동시에 발생했다는 사실은 서술형 콘텐츠에서 충분히 설명한다.

이유:
동일 프로젝트의 여러 사건을 모두 합산하면
하나의 프로젝트가 과도하게 높은 점수를 받을 수 있기 때문이다.

단, 여러 사건이 복합적으로 화제성을 높였다는 점은
'왜 화제가 되었나' 섹션에서 반드시 반영한다.

---

## 4. 동일 분야 편중 허용

TOP 5를 분야별로 인위적으로 분산하지 않는다.

예:

- TOP 1: AI Agent
- TOP 2: AI Agent
- TOP 3: AI Agent
- TOP 4: AI Agent
- TOP 5: AI Agent

이와 같이 TOP 5가 모두 같은 분야라도 그대로 유지한다.

원칙:

- 분야 다양성을 위해 낮은 점수의 프로젝트를 억지로 끼워 넣지 않는다.
- 해당 주에 실제로 가장 화제가 된 이슈를 우선한다.
- 특정 분야가 TOP 5를 독점했다면 그것 자체를 해당 주의 중요한 트렌드로 본다.

이 경우 마지막 '이번 주 GitHub 전체 트렌드'에서
특정 분야에 관심이 집중된 이유를 별도로 설명한다.

---

## 5. Critical 보안 이슈 처리

Critical Security Issue는 TOP 5 내부에 포함한다.

다음과 같은 사건이 대표적인 강제 포함 대상이다.

- Critical Security Vulnerability
- Remote Code Execution
- Supply-chain Attack
- Authentication Bypass
- 대규모 Credential Exposure
- 개발 생태계에 광범위한 영향을 주는 Critical 취약점

Critical 보안 이슈가 후보로 확인되면
일반 화제성 점수만으로 자동 탈락시키지 않는다.

---

## 6. Critical 보안 이슈의 순위 결정

Critical 보안 이슈라고 해서 무조건 TOP 1로 배치하지는 않는다.

순위는 다음 요소를 함께 고려한다.

- 영향받는 프로젝트의 규모
- 영향받는 사용자 수
- 공격 가능성
- 실제 악용 여부
- 패치 제공 여부
- 개발 생태계 영향
- 화제성 점수
- 사건의 긴급성

다만 Critical 보안 이슈는
최종 TOP 5 안에는 반드시 포함하도록 한다.

---

## 7. Critical 보안 이슈로 인해 기존 TOP 5가 밀리는 경우

예:

기존 점수 순위:

1. Project A
2. Project B
3. Project C
4. Project D
5. Project E
6. Critical Security Project F

Project F가 Critical 보안 사건에 해당한다면
최종 TOP 5에 포함한다.

이 경우 상대적으로 우선순위가 낮은 일반 후보 1개를 제외한다.

예:

1. Project A
2. Project B
3. Project F - Critical Security
4. Project C
5. Project D

Project E는 최종 TOP 5에서 제외될 수 있다.

정확한 위치는 사건 중요도와 화제성 점수를 함께 고려해 결정한다.

---

## 8. Critical 보안 프로젝트가 이미 TOP 5인 경우

해당 프로젝트가 일반 점수만으로도 이미 TOP 5에 포함되어 있다면
별도의 추가 항목을 만들지 않는다.

해당 프로젝트의 TOP 메시지 안에서:

- 보안 사건
- 영향 범위
- 취약 버전
- 패치 여부
- 권장 대응
- 개발자 반응

을 함께 상세히 설명한다.

필요할 경우 기존 Telegram 특별 경고 메시지도 추가로 보낼 수 있다.

즉:

TOP 5에 포함
+
특별 경고 메시지

두 가지를 동시에 사용할 수 있다.

---

## 9. 여러 Critical 보안 이슈가 동시에 발생한 경우

여러 개의 Critical 보안 이슈가 발생했다면
각각의 영향도를 평가한다.

TOP 5 전체를 무조건 보안 사건으로 채우지는 않지만,
개발 생태계 영향이 큰 사건은 일반 후보보다 우선할 수 있다.

이 경우에도 동일 프로젝트에서 여러 취약점이 발생했다면
하나의 프로젝트 항목으로 통합한다.

---

## 10. 최종 TOP 5 구성 절차

1. 전체 후보의 화제성 점수를 계산한다.
2. 점수순으로 임시 순위를 만든다.
3. 동일 프로젝트의 중복 사건을 탐지한다.
4. 동일 프로젝트의 사건을 하나로 통합한다.
5. 더 높은 순위를 프로젝트의 대표 순위로 유지한다.
6. 빈 순위는 다음 후보로 채운다.
7. Critical 보안 이슈가 TOP 5에 포함되어 있는지 확인한다.
8. 포함되지 않았다면 Critical 이슈를 TOP 5에 강제 포함한다.
9. 동일 분야 편중 여부는 수정하지 않는다.
10. 최종적으로 서로 다른 프로젝트 5개를 확정한다.

---

## 11. 최종 핵심 원칙

- 동일 프로젝트는 TOP 5에서 한 번만 등장한다.
- 동일 프로젝트의 여러 사건은 하나의 항목에 모두 포함한다.
- 대표 순위는 여러 사건 중 가장 높은 순위를 사용한다.
- 중복 제거 후 빈 순위는 다음 후보가 승격한다.
- 분야 다양성을 위한 인위적인 조정은 하지 않는다.
- TOP 5가 전부 같은 분야여도 그대로 유지한다.
- Critical 보안 이슈는 TOP 5 안에 반드시 포함한다.
- Critical 보안 이슈라고 무조건 TOP 1로 배치하지는 않는다.
- 최종 TOP 5는 서로 다른 프로젝트 기준 5개를 유지한다.
