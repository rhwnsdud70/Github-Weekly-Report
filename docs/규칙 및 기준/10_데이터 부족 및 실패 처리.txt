# GitHub 주간 AI·개발 이슈 데이터 부족 및 실패 처리 규칙

## 1. 목적

GitHub 데이터 수집 과정에서 일부 정보가 누락되거나 조회에 실패했을 때,
임의의 수치를 생성하거나 부정확한 판단을 하지 않고
가능한 데이터만으로 안정적으로 분석을 계속하기 위한 처리 기준을 정의한다.

핵심 원칙은 다음과 같다.

- 임의 추정 금지
- 확인할 수 없는 지표는 해당 지표만 미확인 처리
- 다른 정상 데이터로 평가는 계속 진행
- 근거가 지나치게 부족하면 최종 후보에서 제외

---

## 2. 임의 추정 금지

확인할 수 없는 데이터를 임의로 계산하거나 만들어내지 않는다.

금지 예시:

- Star 증가량을 근거 없이 추정
- 확인하지 못한 Trending 순위를 임의로 지정
- Issue 수를 대략적인 숫자로 작성
- 커뮤니티 반응을 실제 확인 없이 생성
- Release 내용을 README만 보고 추측
- 보안 영향 범위를 검증 없이 단정

잘못된 예:

"최근 7일 Star가 약 3,000개 증가한 것으로 보인다."

정확한 근거가 없다면 위와 같이 작성하지 않는다.

권장 처리:

"최근 7일 Star 증가량: 정확한 수치 확인 어려움"

---

## 3. 일부 지표 확인 실패 처리

하나의 지표를 확인하지 못했다고 해서
해당 프로젝트 전체 평가를 중단하지 않는다.

예:

확인 가능:
- Trending 진입
- Major Release
- Issue 활동
- Discussion 활동

확인 불가:
- 정확한 최근 7일 Star 증가량

처리:

- Star 증가량 점수는 미확인 처리
- 나머지 지표는 정상적으로 평가
- 프로젝트 전체는 계속 후보로 유지 가능

---

## 4. 미확인 지표 표기 방식

확인할 수 없는 지표는 다음 표현 중 하나를 사용한다.

- 정확한 수치 확인 어려움
- 데이터 확인 불가
- 해당 기간 데이터 미확보
- 비교 데이터 부족
- 확인 가능한 근거 없음

추정치를 사용해야 하는 상황이 발생하더라도
자동화 기본 규칙에서는 추정하지 않는다.

가능하면 확정 데이터만 사용한다.

---

## 5. 화제성 점수 처리

확인하지 못한 지표는 점수를 임의로 부여하지 않는다.

기본 처리:

- 확인 가능 → 정상 점수 계산
- 확인 불가 → 해당 항목 점수 0점 또는 미평가 처리
- 나머지 지표 → 정상 계산

단, 시스템 내부에서는 가능하면
"실제 0점"과 "미확인"을 구분해서 저장한다.

예:

Star 증가량:
- 상태: 미확인
- 점수: 계산 제외

Trending:
- 상태: 확인
- 점수: 12점

Release:
- 상태: 확인
- 점수: 8점

이 방식으로 데이터 부족과 실제 낮은 활동을 구분한다.

---

## 6. 다른 신호로 계속 평가

일부 지표가 없어도 다음과 같은 다른 강한 신호가 존재하면 후보 평가를 계속한다.

예:

- Trending 상위권
- Major Release
- Critical Security Issue
- Issue / PR 급증
- 활발한 Discussion
- 라이선스 변경
- API 폐기
- 프로젝트 종료
- 대규모 Breaking Change

예시:

Star 증가량:
확인 불가

하지만:
- Trending Top 5
- Major Release
- Issue 활동 +200%

→ 후보 유지 및 정상 평가

---

## 7. 핵심 데이터 부족 여부 판단

모든 지표가 동일한 중요도를 가지지는 않는다.

다음 중 최소 하나 이상의 강한 근거가 존재하면
후보 유지 가능성이 있다.

강한 근거:

- Trending 진입
- 확인 가능한 Star 급증
- Major Release
- Critical / High Security 사건
- Issue / PR 활동 급증
- 중요한 License / API 변화
- 커뮤니티에서 명확한 논의 증가
- 프로젝트 종료 / 유지보수 중단

이런 근거가 전혀 없다면 후보 신뢰도가 낮다고 판단한다.

---

## 8. 근거 부족에 따른 후보 제외

다음과 같은 경우 최종 후보에서 제외한다.

- Star 변화 확인 불가
- Trending 확인 불가
- Issue / PR 활동 확인 불가
- Release 없음 또는 확인 불가
- 커뮤니티 논의 근거 없음
- 특별 이벤트 없음
- 외부 자료만 있고 GitHub 내부 근거가 없음

즉, 화제라고 판단할 충분한 근거가 없는 경우 제외한다.

원칙:

"정보가 부족하므로 화제라고 추정"하지 않는다.

---

## 9. 최소 근거 기준

최종 TOP 5 후보로 유지하려면
다음 중 최소 2개 이상의 독립적인 신호가 있는 것을 권장한다.

예:

- Star 급증
- Trending 진입
- Issue / PR 활동 증가
- Major Release
- 활발한 Discussion
- Security 사건
- License / API 변화

예외:

Critical Security Issue와 같이
단일 사건만으로도 개발 생태계 영향이 충분히 큰 경우에는
단일 강한 근거만으로도 후보 유지 가능하다.

---

## 10. 커뮤니티 의견 데이터 부족 처리

GitHub Issues / Discussions / PR 댓글이 충분하지 않은 경우
'개발자들은 무엇을 이야기하고 있나' 섹션을 억지로 채우지 않는다.

가능한 처리:

- "아직 충분한 공개 논의가 확인되지 않음"
- "현재 GitHub 내부 커뮤니티 논의는 제한적임"
- "유의미한 의견 패턴을 판단하기에는 데이터가 부족함"

금지:

- 소수 댓글을 다수 의견처럼 표현
- 외부 SNS 반응을 GitHub 개발자 전체 의견처럼 표현
- 실제 논의가 없는데 찬반 구조를 만들어냄

---

## 11. Release 정보 부족 처리

Release 정보가 없거나 불완전한 경우:

- Major Release 여부를 임의 판단하지 않는다.
- README 변경만으로 Release를 추정하지 않는다.
- 공식 Release / Changelog가 확인될 때만 Release 점수를 부여한다.

표기 예:

"주요 Release: 확인되지 않음"

---

## 12. Trending 정보 부족 처리

Trending 순위를 정확히 확인하지 못한 경우:

- 순위를 임의로 생성하지 않는다.
- 진입 여부만 확인 가능하면 진입 기준 점수 사용
- 진입 여부도 확인할 수 없으면 미확인 처리

예:

정확한 순위 확인 불가
+
Trending 진입 확인

→ "Trending 진입 확인 / 정확한 순위 확인 어려움"

---

## 13. 이전 주 데이터 누락 처리

직전 주 Snapshot이 없는 경우:

- Star 증가량을 Snapshot 차이로 계산하지 않는다.
- 화제성 점수 변화도 계산하지 않는다.
- 신규 프로젝트 또는 신규 추적 대상으로 처리한다.

표기:

- 이전 Star 수: 데이터 없음
- 전주 대비 점수 변화: 비교 불가

이후 현재 데이터를 저장하여 다음 주부터 비교한다.

---

## 14. 일부 데이터 수집 시스템 실패

GitHub 데이터 수집의 특정 경로가 실패한 경우
다른 경로의 데이터 수집은 계속 진행한다.

예:

GitHub Trending 수집 실패

하지만:
- 전체 조건 검색 성공
- Issue 검색 성공
- Release 검색 성공

→ 전체 작업을 중단하지 않는다.

가능한 데이터로 후보 분석을 계속한다.

---

## 15. 전체 분석 중단 기준

다음과 같이 핵심 데이터 소스가 광범위하게 실패한 경우에는
정상적인 주간 TOP 5를 생성하지 않는 것을 허용한다.

예:

- GitHub Repository 조회 전반 실패
- Issue / Release 조회 대부분 실패
- 후보 검증이 불가능한 수준의 데이터 부족
- 신뢰할 수 있는 TOP 5 선정이 불가능

이 경우:

- 임의로 TOP 5를 생성하지 않는다.
- 불완전한 보고서를 정상 보고서처럼 보내지 않는다.

가능하다면 Telegram에는
"이번 주 데이터 수집 문제로 인해 정상적인 보고서를 생성하지 못함"
과 같은 실패 안내만 전송할 수 있다.

---

## 16. Telegram 메시지 표기 원칙

데이터 부족이 있는 경우 해당 항목에서 명확하게 표시한다.

예:

📈 이번 주 주요 지표

⭐ 현재 Star: 8,420  
🚀 최근 7일 Star 증가: 정확한 수치 확인 어려움  
🔥 GitHub Trending: 진입 확인  
💬 Issue / PR 활동: 전주 대비 +120%  
📦 주요 Release: v2.0

확인되지 않은 값을 공란으로 두기보다
미확인 사실을 명확하게 표시한다.

---

## 17. 최종 검증 체크

TOP 5 확정 전 각 후보에 대해 확인한다.

- 확인하지 못한 수치를 임의로 만들지 않았는가
- 미확인 지표를 실제 0과 구분했는가
- 다른 근거가 충분한가
- 최소 근거 기준을 만족하는가
- 커뮤니티 의견을 과도하게 일반화하지 않았는가
- Release / Trending 정보를 추측하지 않았는가
- 이전 주 데이터가 없을 때 잘못 비교하지 않았는가
- 근거가 지나치게 부족한 후보를 제외했는가

---

## 18. 핵심 처리 흐름

데이터 조회
→ 정상 / 미확인 구분
→ 미확인 데이터 추정 금지
→ 확인 가능한 지표만 계산
→ 다른 신호로 계속 평가
→ 최소 근거 수준 확인
→ 근거 충분: 후보 유지
→ 근거 부족: 후보 제외

---

## 19. 핵심 원칙 요약

1. 임의 추정하지 않는다.
2. 확인 불가 지표는 명확하게 미확인 처리한다.
3. 하나의 데이터가 없어도 전체 분석을 중단하지 않는다.
4. 다른 정상 신호로 평가를 계속한다.
5. 실제 0과 데이터 미확인을 구분한다.
6. 최소한의 독립적인 근거를 확보한다.
7. 근거가 너무 부족하면 후보에서 제외한다.
8. Critical 보안 사건은 단일 강한 근거로도 예외적으로 유지할 수 있다.
9. 광범위한 데이터 실패 시 억지로 TOP 5를 만들지 않는다.
10. 정확성보다 완성도를 우선하지 않는다.
