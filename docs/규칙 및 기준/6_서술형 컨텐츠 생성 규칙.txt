GitHub 주간 AI·개발 이슈 서술형 콘텐츠 생성 규칙 - 최종본

목적
매주 선정된 GitHub TOP 5 이슈에 대해
"왜 화제가 되었는가", "무엇을 하는 프로젝트인가",
"개발자에게 왜 중요한가", "개발자들은 무엇을 이야기하고 있는가",
"주의할 점"과 같은 서술형 콘텐츠를 일관되고 신뢰성 있게 생성하기 위한 기준을 정의한다.

핵심 원칙:
- GitHub 원문 근거를 먼저 수집한다.
- 수집한 사실과 의견을 분리한다.
- 개별 댓글 하나를 전체 커뮤니티 의견처럼 일반화하지 않는다.
- 화려한 표현보다 근거 기반 설명을 우선한다.
- 확인할 수 없는 사실은 추정하거나 만들어내지 않는다.

==================================================
1. 근거 자료 우선순위
==================================================

서술형 콘텐츠 작성 시 다음 순서로 근거를 우선한다.

1순위: GitHub Repository README / 공식 문서
용도:
- 프로젝트가 무엇을 하는지
- 주요 기능
- 기술적 특징
- 설치 및 사용 방식
- 기존 기술과의 차이

2순위: GitHub Release Notes / Changelog
용도:
- 이번 주 주요 업데이트
- 신규 기능
- Breaking Change
- 성능 개선
- API 변경
- 버전 전환
- 정식 출시 여부

3순위: GitHub Issues
용도:
- 실제 사용자 버그 보고
- 기능 요청
- 문제점
- 사용 경험
- 기술적 논쟁
- 유지보수 이슈

4순위: GitHub Discussions
용도:
- 개발자 반응
- 사용 경험 공유
- 방향성 논의
- 긍정/부정 의견
- 커뮤니티 논쟁

5순위: Pull Request
용도:
- 실제 구현 중인 변화
- 핵심 기능 개발 상태
- 기술적 설계 논쟁
- 코드 수준의 변경 내용

6순위: GitHub Security Advisory
용도:
- 보안 취약점
- 영향 버전
- 패치 여부
- 권장 조치

외부 기사, 블로그, SNS는 보조 자료로만 사용한다.
가능하면 핵심 주장에는 GitHub 내부 원문을 우선 사용한다.

==================================================
2. 사실과 의견 분리
==================================================

서술형 콘텐츠를 작성하기 전에 수집한 정보를 다음 두 종류로 분류한다.

[사실]
- Release가 실제로 있었음
- 특정 기능이 추가됨
- Star가 증가함
- Issue가 생성됨
- 특정 버그가 보고됨
- 특정 버전이 영향을 받음

[의견]
- 사용하기 쉽다는 평가
- 기존 도구보다 낫다는 주장
- Production에 쓰기 이르다는 우려
- 성능이 좋다는 사용자 경험
- 다른 프레임워크를 대체할 수 있다는 주장

작성 시 사실과 의견을 섞지 않는다.

예:
잘못된 표현:
"이 프로젝트는 기존 도구보다 확실히 더 좋다."

권장 표현:
"일부 개발자들은 기존 도구보다 설정이 단순하다고 평가하고 있다."

==================================================
3. '왜 화제가 되었나' 작성 규칙
==================================================

이 섹션은 단순 요약이 아니라
"배경 → 직접 계기 → 관심 증가 → 반응 이유" 구조로 작성한다.

권장 구조:

1. 배경
- 원래 어떤 프로젝트였는지
- 기존에 어떤 위치에 있었는지

2. 직접적인 계기
- 이번 주 어떤 Release, 기능, 사건, 발표가 있었는지

3. 관심 증가
- Star, Trending, Issue/PR 활동 등 어떤 변화가 나타났는지

4. 반응 이유
- 왜 개발자들이 관심을 보였는지
- 기존 기술과 비교해 무엇이 달랐는지
- 실제 사용 가치가 무엇인지

작성 원칙:
- "Star가 많이 늘어서 화제"라고 끝내지 않는다.
- 관심 증가의 원인을 반드시 설명한다.
- 필요하면 여러 문단으로 충분히 작성한다.
- 단순 홍보성 표현은 피한다.
- 단기 유행인지 기술적 이유가 있는지 구분해 설명한다.

==================================================
4. '무엇을 하는 프로젝트인가' 작성 규칙
==================================================

이 섹션은 프로젝트 자체를 이해시키는 목적이다.

포함 내용:
- 프로젝트의 목적
- 주요 기능
- 핵심 기술 구조
- 사용 대상
- 기존 유사 기술과의 차이
- 이번 업데이트에서 달라진 점

작성 원칙:
- README와 공식 문서를 우선 참고한다.
- 기술을 처음 접한 개발자도 이해할 수 있도록 작성한다.
- 과도한 마케팅 문구를 그대로 사용하지 않는다.
- 기능 나열만 하지 말고 실제 사용 목적을 함께 설명한다.

==================================================
5. '개발자에게 왜 중요한가' 작성 규칙
==================================================

이 섹션은 프로젝트 설명과 분리한다.

핵심 질문:
"이 변화 때문에 실제 개발자의 작업 방식이 어떻게 달라질 수 있는가?"

다음 관점 중 실제 관련 있는 항목만 사용한다.

- 개발 생산성
- 비용
- 성능
- 안정성
- 보안
- 유지보수
- 학습 난이도
- 배포 방식
- 인프라 구성
- API 사용 방식
- 기존 기술 대체 가능성
- 생태계 영향
- 개발 프로세스 변화

작성 원칙:
- 기능 설명을 반복하지 않는다.
- 개발자 입장에서의 실질적인 영향을 설명한다.
- 가능성은 가능성으로 표현한다.
- 확정되지 않은 미래 효과를 단정하지 않는다.

==================================================
6. '개발자들은 무엇을 이야기하고 있나' 작성 규칙
==================================================

이 섹션은 개별 댓글 나열이 아니라
여러 의견에서 반복되는 패턴을 정리한다.

기본 분류:

A. 긍정적인 의견
- 높게 평가하는 기능
- 사용성 장점
- 생산성 향상
- 기존 도구 대비 장점

B. 우려하거나 비판하는 의견
- 버그
- 안정성
- 성능
- API 설계
- 유지보수
- 보안
- 라이선스
- 과도한 기대
- Production 적용 문제

C. 논쟁 중인 부분
- 기존 프로젝트 대체 가능성
- 설계 방향성
- 성능과 편의성의 trade-off
- API 구조
- 라이선스 정책
- 프로젝트 방향성

작성 방식:
1. Issue, Discussion, PR 댓글에서 핵심 주장을 추출한다.
2. 비슷한 의견끼리 묶는다.
3. 반복되는 패턴을 찾는다.
4. 긍정 / 우려 / 논쟁으로 분류한다.
5. 왜 그런 의견이 나오는지도 함께 설명한다.

==================================================
7. 커뮤니티 의견 일반화 기준
==================================================

의견의 근거 수준에 따라 표현 강도를 조정한다.

여러 Issue/Discussion에서 반복되는 경우:
- "여러 개발자들이..."
- "반복적으로 제기되는 의견은..."

한 Discussion에서 다수 의견이 확인되는 경우:
- "해당 Discussion에서는..."
- "해당 토론에서는 다수의 사용자가..."

소수 의견인 경우:
- "일부 개발자는..."
- "몇몇 사용자는..."

댓글 1~2개 수준인 경우:
- "한 사용자 또는 일부 사용자가..."
- 전체 커뮤니티 의견처럼 일반화하지 않는다.

절대 사용하지 말아야 할 표현:
- "모든 개발자들이..."
- "대부분의 개발자들이..." (근거가 충분하지 않은 경우)
- "커뮤니티 전체가..."
- "개발자들은 모두..."

==================================================
8. 커뮤니티 의견 강도 분류
==================================================

의견 수집 시 내부적으로 다음처럼 판단할 수 있다.

[강한 패턴]
- 여러 Issue/Discussion에서 반복
- 유사 의견이 다수 존재
- 공식 Maintainer도 관련 내용을 언급

[중간 패턴]
- 한 Discussion 또는 Issue에서 반복
- 여러 명이 같은 문제를 보고

[약한 패턴]
- 소수 댓글
- 단일 사용자 경험

Telegram 메시지에서는 강도에 맞춰 표현을 조절한다.

==================================================
9. '주의할 점' 작성 규칙
==================================================

이 섹션은 부정적인 내용을 억지로 만들지 않는다.

다음과 같은 실제 근거가 있을 때만 작성한다.

- Experimental / Beta 표시
- 반복되는 버그 보고
- Production 안정성 부족
- API 변경 가능성
- Breaking Change
- 라이선스 제한
- Security Advisory
- 플랫폼 호환성 문제
- 성능 검증 부족
- 유지보수 빈도 저하
- 문서 부족
- 특정 환경에서의 문제

표현 예시:

강한 근거:
"현재 v1.2에서 해당 버그가 확인되고 있다."

중간 근거:
"여러 사용자가 Windows 환경에서 동일한 문제를 보고하고 있다."

약한 근거:
"일부 사용자가 특정 환경에서 문제를 보고하고 있어 추가 검증이 필요하다."

장기 검증 부족:
"아직 장기간 운영 사례가 충분하지 않아 Production 안정성은 더 지켜볼 필요가 있다."

==================================================
10. 외부 자료 사용 규칙
==================================================

외부 기사, 블로그, SNS를 사용할 경우:

- GitHub 내부 자료가 부족할 때 보조적으로 사용
- 외부 자료만으로 중요한 기술적 사실을 단정하지 않음
- 가능하면 GitHub 원문과 교차 확인
- 개인 블로그나 SNS의 의견은 커뮤니티 전체 의견으로 일반화하지 않음

==================================================
11. 링크 선정 규칙
==================================================

각 TOP 5 항목에 다음 링크를 우선 포함한다.

필수:
- Repository URL

선택:
- 주요 Issue 1~3개
- 주요 Discussion 1~3개
- 중요한 Pull Request
- 주요 Release
- Security Advisory

원칙:
- 실제 서술형 내용의 근거가 되는 링크를 우선한다.
- 중요하지 않은 링크를 많이 나열하지 않는다.

13. 최종 검증 규칙
==================================================

각 TOP 5 항목을 발송하기 전에 다음을 확인한다.

- 모든 주요 주장이 실제 근거를 가지고 있는가
- Star 증가만으로 화제 이유를 설명하고 있지 않은가
- Release 또는 사건의 직접 계기를 설명했는가
- 사실과 의견을 구분했는가
- 소수 의견을 전체 개발자 의견처럼 표현하지 않았는가
- 긍정 의견과 우려 의견을 균형 있게 다뤘는가
- 논쟁이 없는데 억지로 논쟁을 만들지 않았는가
- 주의할 점을 과장하지 않았는가
- 확인할 수 없는 수치를 생성하지 않았는가
- 외부 자료를 GitHub 원문보다 우선하지 않았는가
- 관련 링크가 실제 서술 내용을 뒷받침하는가

==================================================
14. 작성 톤
==================================================

- 기술적으로 명확하게 작성한다.
- 과도하게 흥분된 표현을 피한다.
- 지나치게 홍보성 문구를 사용하지 않는다.
- 단순 뉴스 기사처럼 쓰기보다 개발자 관점의 주간 리포트로 작성한다.
- 필요한 경우 길게 설명하되 반복은 줄인다.
- 불확실한 내용은 불확실하다고 명시한다.
- 판단과 사실을 구분한다.

==================================================
15. 핵심 원칙 요약
==================================================

- GitHub 원문 근거 우선
- 사실과 의견 분리
- 원인 → 변화 → 반응 구조로 화제 이유 설명
- 커뮤니티 의견은 패턴으로 요약
- 의견 강도에 맞는 표현 사용
- 개발자에게 미치는 실제 영향 설명
- 확인 가능한 리스크만 주의사항에 포함
- 불확실한 정보는 단정하지 않음
- 최종 목표는 "왜 이번 주 이 이슈가 중요했는지 개발자가 이해할 수 있게 설명하는 것"
